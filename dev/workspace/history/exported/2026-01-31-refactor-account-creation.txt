  The tenancy architecture has two independent layers:

  1. URL path tenancy (always on) — The AccountSlug::Extractor middleware strips
   a 7+ digit account ID from the URL path, sets Current.account, and Rails
  treats the app as mounted at that prefix. This is structural and doesn't
  change between modes.
  2. Signup gating (controlled by MULTI_TENANT env var) —
  Account.accepting_signups? is the single predicate that opens or closes the
  door to new account creation. It returns true if multi-tenant mode is enabled
  OR if no accounts exist yet (bootstrap escape hatch).

⏺ Here's the full trace of what happens:

  Flow: Single-tenant user → menus/show → new account

  1. User logs in → magic link validated → session started
     Sessions::MagicLinksController#sign_in
       → redirect to after_authentication_url → landing_url (no account slug)

  2. Browser hits /landing → LandingsController
     → require_account fires → Current.account is nil
     → redirects to session_menu_path(script_name: nil)

  3. Sessions::MenusController#show
     → @accounts = Current.identity.accounts.active (1 account)
     → CURRENT: @accounts.one? → auto-redirect to account (user never sees menu)
     → PROPOSED: @accounts.one? && !allow_single_tenant_accounts? → show the
  menu

  4. User sees menu with "Sign up for a new Fizzy account" link
     → clicks link to new_signup_path

  5. SignupsController before_action chain:
     a. redirect_tenanted_request → no slug, passes ✓
     b. resume_session → resumes existing session, sets Current.identity ✓
     c. redirect_authenticated_user → authenticated? is TRUE
        → REDIRECTS to new_signup_completion_path (halts chain)
     d. enforce_tenant_limit → NEVER REACHED

  6. Signups::CompletionsController#new
     → disallow_account_scope (no account needed) ✓
     → require_authentication (session exists) ✓
     → NO enforce_tenant_limit check exists here
     → renders the completion form (enter your name)

  7. POST /signups/completions → Signup#complete
     → Account.create_with_owner (no tenancy check)
     → New account created ✓

  The answer is yes — it works. The completions controller has no tenant limit
  gate at all. The enforce_tenant_limit check only exists in SignupsController,
  and authenticated users skip past it because redirect_authenticated_user fires
   first and redirects them straight to completions.

  Two things worth flagging:

  1. The current gating is UI-based, not a hard check. Even today, without your
  proposed changes, any authenticated user who navigates directly to
  /signups/completions/new can create a new account in single-tenant mode. The

  ---
  On your second question about improvements — the proposed SingleTenantable
  works, but introducing a parallel concern means tenancy predicates live in two
   places. Three alternatives worth considering:

  1. Extend MultiTenantable directly — keep all tenancy logic in one concern:

  module Account::MultiTenantable
    included do
      cattr_accessor :multi_tenant, default: false
      cattr_accessor :allow_account_creation, default: false
    end

    class_methods do
      def accepting_signups?
        multi_tenant || Account.none?
      end

      def allow_account_creation?
        multi_tenant || allow_account_creation || Account.none?
      end
    end
  end

  Then cancellable? and the menus controller use allow_account_creation? while
  the public signup gate stays on accepting_signups?. One concern, two
  predicates, clear separation of "public signup" vs "authenticated account
  creation."

  2. Parameterize accepting_signups? — same concern, single predicate with
  context:

  def accepting_signups?(for_existing_identity: false)
    multi_tenant || Account.none? || (for_existing_identity &&
  allow_account_creation)
  end

  Keeps one method name but the call sites become more expressive about intent.

  3. No model predicate at all — the menus controller already controls access by
   auto-redirecting. Just check the env var directly in the controller and view,
   skipping the model layer entirely. Simpler but less testable and spreads
  configuration knowledge into the controller.

  Option 1 is the cleanest. It follows the existing pattern, keeps tenancy
  decisions in one place, and the naming (allow_account_creation?) describes the
   intent better than allow_single_tenant_accounts? — since it's really about
  whether authenticated users can create accounts regardless of tenancy mode.

❯ oohh admin restriction, but how would this work because users are admins

⏺ That's a good catch. The role hierarchy (owner/admin/member) is per-User,
  per-Account. An identity could be an owner in one account and a member in
  another. There's no identity-level role, so "is this person an admin" doesn't
  have a single answer.

  Checking against the current account's role would be arbitrary — why should
  your permissions in Account A determine whether you can create Account B? And
  if you're a member in your only account, you'd be locked out of creating your
  own.

  The realistic options for limiting creation are identity-level, not
  role-level:

  - Account count cap — Current.identity.accounts.active.count < N in the
  completions controller. Simple, clear, no role confusion. The N could be an
  env var.
  - Staff flag — Identity already has a staff boolean (identities.yml shows
  david with staff: true). Could gate account creation on
  Current.identity.staff?. But this is meant for 37signals internal use, not
  self-hosted operators.
  - Accept it — anyone invited can create accounts. The invite itself is the
  trust boundary. If you handed someone a join code, you trust them enough.

  The count cap is the cleanest if you want a limit. Otherwise, the
  invite-as-trust-gate is reasonable for a self-hosted scenario where you
  control who gets join codes.
